# Замеры и профилирование

**После перехода на `byte` (06.10.2026):** вход и результат всех вариантов — `byte[,]`; коэффициенты ядра и накопление суммы остаются `float`. Ниже встречается описание прежних замеров на `double`/`float`; эти численные результаты и сопоставления нужно считать историческими и измерить заново. Для текущего GPU-пути профиль 1 измеряет весь вызов, профиль 2 отдельно синхронизирует и показывает передачу, ядро и возврат.

## Запуск

Из папки проекта:

```powershell
dotnet run -c Release
```

В режимах 1, 2, 3, 4, 5 и 7 каждый вариант выполняется один раз для прогрева, затем ровно 25 раз для измерения. Прогрев не входит в статистику. В режиме 2 это 25 запусков для внешнего параллелизма с последовательной свёрткой, ещё 25 со строковой и 25 со столбцовой. В режиме одного CPU-файла проверяются все три стратегии. Загрузка одиночного файла находится вне измерений свёртки; время папки включает её обработку целиком. Дополнительный вызов для сохранения результата одиночного файла не является измеряемым прогоном.

Unified теперь тоже имеет 25 повторений. Каждый повтор создаёт новый UnifiedProcessor и GPU-агентов; инициализация и освобождение входят во внешний замер. Для одиночного GPU-файла процессор создаётся заранее и используется повторно: его подготовка не входит в время отдельной свёртки.

BenchmarkDotNet: 25 измеряемых итераций для каждого метода и каждого ImageSize, отдельно 3 прогревочные итерации. Одна измеряемая итерация может содержать несколько вызовов метода — число вызовов подбирает BenchmarkDotNet. Выбросы не удаляются. Его подготовка, pilot/overhead-измерения и MemoryDiagnoser — дополнительные служебные этапы, не новые варианты свёртки. Встроенный профиль приложения в BenchmarkDotNet не включается.

## Выбор профиля

После выбора режима программа спрашивает:

- `0`: общие времена и 25 результатов, без сбора стадий.
- `1` или Enter: стадии, ожидания, CPU-время процесса, выделения GC и параметры. Вызов GPU с байтовыми пикселями измеряется целиком без дополнительных ожиданий между этапами.
- `2`: то же плюс разделение GPU-вызова на передачу, ядро и получение результата. Это добавляет Synchronize и может изменить поведение и скорость. Такой профиль нужен для диагностики, его времена нельзя смешивать с режимами 0/1.

Все текущие GPU-варианты используют байтовые вход и результат. Последовательная GPU-папка отдельно замеряет передачу, ядро и возврат; Unified использует цельный вызов GPU при профиле 0/1.

Для новых диагностических замеров сначала используйте профиль 1. Для разбора передачи/вычислений GPU выполните отдельную серию профиля 2. Не запускайте тесты одновременно. Поддерживайте одинаковый набор входов, питание, настройки и фоновую нагрузку. Новые 25 прогонов не запускаются автоматически для всех чисел агентов: выбранная конфигурация получает свои 25 измерений; затем можно запустить программу с другой конфигурацией.

## Где результаты

Программа печатает абсолютный путь. Папка имеет вид:

`MeasurementResults/дата_время_идентификатор/название-режима/`

- `times.csv`: все 25 времён в миллисекундах, точка как десятичный разделитель.
- `run-01.json` … `run-25.json`: общий интервал, параметры и профиль каждого запуска.
- `summary.json`: среднее, медиана, минимум, максимум, стандартное отклонение с делителем n, сводка стадий.
- `summary.txt`: читаемая сводка, также выводится в консоль.

При ошибке измеряемого запуска сохраняется JSON с ошибкой и имеющимся профилем; ошибка не скрывается. Неполную серию нельзя выдавать за 25 успешных измерений. Полная сводка создаётся только после успешных 25 запусков. Прогревы выполняются до записи измеряемых профилей.

Пришлите папку результатов целиком или её ZIP. Одной медианы недостаточно для поиска причины разброса. Исходные изображения и папки обработанных фотографий для анализа профиля не нужны, если исходный набор не менялся.

## Как читать стадии

| Ключ | Содержание |
|---|---|
| reader.load | Загрузка, декодирование, серый массив |
| io.decode_read | Открытие и декодирование через ImageSharp |
| io.grayscale_allocate | Выделение массива и перевод в серый |
| reader.wait_slot | Ожидание лимита изображений в работе |
| reader.enqueue | Добавление входа в ограниченную очередь, включая ожидание места |
| cpu.wait_input / gpu.wait_input | Получение задания и ожидание входного канала |
| cpu.convolve.Sequential / ParallelByRows / ParallelByColumns | Собственная свёртка и выделение результата |
| cpu.enqueue_result / gpu.enqueue_result | Передача результата писателю, включая ожидание места |
| writer.wait_input | Ожидание результата для сохранения |
| writer.save | Вся подготовка и сохранение результата |
| io.output_allocate | Получение буфера выходного Image<L8> |
| io.encode_write | Кодирование и запись файла; без предшествующего заполнения пикселей |
| imagesharp.allocate | Получение Image<L8> |
| imagesharp.pack | Заполнение L8 из байтовой матрицы |
| imagesharp.blur | Mutate + BoxBlur |
| imagesharp.unpack | Выделение byte[,] и извлечение результата |
| imagesharp.total | Полный адаптированный библиотечный вызов |
| gpu.initialize | Создание контекста/акселератора и загрузка GPU-ядер |
| gpu.prepare_buffers | Проверка, создание/переиспользование буферов и подготовка коэффициентов |
| gpu.byte.total | Полный вызов GPU-свёртки, включая подготовку и получение результата |
| gpu.byte.prepare_wait | Ожидание после подготовки буферов в подробном профиле |
| gpu.*.upload_wait | Передача изображения на GPU с ожиданием |
| gpu.*.kernel_wait | Запуск ядра, его выполнение и ожидание |
| gpu.*.download_result | Получение массива результата в ОЗУ |
| setup.memory_limit | Чтение метаданных файлов и расчёт лимита памяти |

`Count` — число вызовов, `SumMilliseconds` — сумма длительностей, `MeanMilliseconds` — среднее на вызов. Ожидания потребляющего перечислителя включают последний вызов, определяющий завершение канала, поэтому их количество может быть равно файлы + агенты. Сводка показывает медиану суммарной длительности стадии за один прогон; это не медиана отдельных файлов.

Таймеры стадий измеряют elapsed time, а не чистые CPU-инструкции. Паузы GC, вытеснение ОС и ожидания ресурсов могут попасть внутрь стадии. Поле CpuMilliseconds относится ко всему процессу.

### Не складывать все строки профиля

Чтение, вычисление и запись конвейера перекрываются. Ожидания всех работников суммируются. Пять работников могут суммарно ждать 40 секунд за 10 секунд реального времени. Кроме того, `io.decode_read` вложен в `reader.load`, а `imagesharp.blur` вложен в `imagesharp.total`. Их повторное сложение дважды учтёт одну работу.

Суммарное ожидание / (число агентов данной роли × время прогона) даёт ориентировочную долю ожидания, с оговоркой о запуске и завершении конвейера. Это не измерение загрузки физических ядер.

## Как искать ограничение

- Читатель занят почти весь проход, cpu/gpu.wait_input велики: вычислители ждут подготовку входов.
- writer.save близок ко времени работы одного писателя, enqueue_result велик: выходная очередь заполняется, ограничивает сохранение.
- reader.wait_slot велик: закончились разрешения на изображения в работе. Это может быть следствием медленного писателя, а не нехватки физической ОЗУ.
- cpu.convolve велик, ожидания малы: вычислительная стадия может ограничивать поток.
- imagesharp.pack/unpack велики: заметную часть библиотечного пути занимают адаптеры представлений.
- gpu.initialize велик: подготовка устройства существенна для выбранных границ замера.

Это признаки для совместного анализа, а не автоматическое доказательство одной причины. Физическое чтение диска отдельно от декодирования не измеряется. Также не измеряются аппаратные cache misses, TLB misses, температура и частоты.

## Строки и столбцы

В Metadata.layout сохраняются размер элемента и фактические смещения между соседними элементами прямоугольного массива, полученные через Unsafe.ByteOffset:

- nextColumnBytes: переход от [0,0] к [0,1], то есть вправо по строке;
- nextRowBytes: переход от [0,0] к [1,0], то есть вниз по столбцу.

Для текущего byte-массива шириной 3840 это 1 и 3840 байт. Для единственного столбца/строки соответствующий сосед отсутствует и значение равно null. Измерение доказывает шаг расположения элементов, но не число промахов кэша. Таймеры показывают, сколько заняли соответствующие стратегии.

## Почему Unified GPU быстрее последовательной GPU-папки

В последовательной GPU-папке выполняется цепочка одного файла целиком, затем следующего. В Unified читатели, GPU-агенты и писатели могут одновременно заниматься разными изображениями. Поэтому задержки стадий перекрываются и общая скорость не равна сумме их времён.

Старые 31,332 с и 11,419 с относятся к прежним реализациям и не являются результатами версии с единым байтовым представлением. По умолчанию сейчас один читатель и один писатель, их числа можно указать при запуске пункта 7. Они сохраняются в имени серии и профиле. 0 CPU означает отсутствие CPU-свёртки, но чтение, кодирование и управление GPU всё равно работают на CPU.

Для сопоставления старых конфигураций выберите в Unified: CPU=0, GPU=2, чтение=2, запись=2. Для текущего варианта 1/1 просто нажмите Enter на вопросах чтения и записи. Это разные серии, их результаты нельзя объединять. Два GPU-агента на одной RTX не означают две физические видеокарты.

## ImageSharp без промежуточных массивов (пункт 9, 23.09)

Пункт 4 использует обёртку: `byte[,]` → `Image<L8>` → `BoxBlur(1)` → `byte[,]`. Пункт 9 запускает прямой ImageSharp-путь: `Image.Load<Rgba32>` → перевод в `Image<L8>` → `BoxBlur(1)` → сохранение. В обоих случаях рабочее изображение фильтра — байтовое. Между обёрткой и прямым путём возможна разница округления яркости при чтении JPEG; её проверяют по пикселям.

Таймеры imagesharp.native: decode_read (загрузка и декодирование), output_allocate (выделение изображения L8), grayscale (заполнение яркостей), blur (библиотечный фильтр), encode_write (кодирование и запись), file_total (весь файл, включает остальные стадии). setup.memory_limit — предварительная оценка лимита памяти. Для ограничения числа одновременных файлов используется оценка 8 байт/пиксель с учётом временного декодированного изображения и буферов; это не точный пик потребления. Реальное parallelFiles записывается в JSON профиля.

Запуск: dotnet run -c Release --project ImageConvolution/ImageConvolution.csproj. Пункт 4 или 9, профиль 0 для полного времени либо 1 для диагностики, папка C:\Test4K. Каждый запуск: отдельный прогрев и 25 измерений. Выход пункта 9: C:\ImageSharp_Native_Output при входе C:\Test4K. Сравнивать оба варианта при одинаковом профиле и наборе входов; желательно чередовать серии. Не запускать серии одновременно. Детальный профиль GPU (2) для этого сравнения не нужен.

Профиль фиксирует прошедшее время вызовов, включая вытеснение потока, а не CPU cycles. Очередные операции включают как ожидание, так и собственную стоимость. Диск не изолирован от кодеков и файлового кэша; завершение Save не означает принудительный сброс на физический носитель. GPU kernel_wait включает запуск и ожидание завершения; режим 2 добавляет синхронизации. Эти ограничения не делают показания неправильными, но задают пределы их интерпретации.

В summary.txt дополнительно выводятся уже собиравшиеся CPU-время процесса, управляемые выделения и количества GC. CPU-время включает все потоки/стадии; выделения не равны пику занятой памяти.

Для столбцов уже есть cpu.convolve.ParallelByColumns и layout со смещениями. Таймер на каждый пиксель не добавлять: он исказит горячий цикл и не измерит промахи кэша. Контроль: строки/столбцы на одном массиве без файлов (пункт 1 или BenchmarkDotNet), затем аппаратные счётчики cache misses/TLB/memory stalls через Intel VTune при доступности на данном CPU и Windows. Для причинного сравнения дополнительно полезен последовательный обход по строкам/столбцам без влияния планировщика. Пока такого контроля и аппаратных данных нет, локальность — обоснованное объяснение, а не измеренная доля замедления.

Следующие приоритеты: изолированный ImageSharp benchmark без обёртки с восстановлением исходных пикселей вне измерения; CPU float по строкам/столбцам; сравнение Unified с фиксированными GPU/R/W при изменении только CPU. Блочная свёртка и разделимый BoxBlur — отдельные оптимизированные методы после базовых измерений; не подменять ими существующие варианты и не смешивать общую свёртку произвольного ядра с алгоритмом только для разделимых ядер.

## Контроль локальности (пункты 10 и 11)

Пункт 10: один выбранный файл загружается один раз, вне измерений. Три последовательных варианта Rows, Columns, BlockedColumns вызывают общий ConvolutionCore; математика пикселя, порядок коэффициентов, тип double, BoxBlur 3x3 и Extend одинаковы. Варианты не используют Parallel.For. BlockedColumns проходит плитки 32x32, внутри каждой — по столбцам. Размер 32 является одной проверяемой настройкой, не доказанным оптимумом. Каждый вариант: один прогрев и 25 измерений. Время включает создание результата, весов и смещений, а также возможную GC; не является исключительно временем арифметики. Профиль стадий отключён. Старые режимы сохраняют прежний порядок обхода.

Пункт 11: отдельный BenchmarkDotNet-класс LocalityBenchmarks без создания GPU. Два размера: 1024x1024 и 3840x2160; одинаковые псевдослучайные данные Random(42), 3 прогревочные и 25 измерительных итераций. Вход создаётся в GlobalSetup. Три метода возвращают результат, MemoryDiagnoser фиксирует выделения. Вычисляющий поток один, но процесс .NET может иметь служебные потоки. Не запускайте пункты 10 и 11 одновременно. Для первого ответа достаточно пункта 10; BDN полезен для более воспроизводимой проверки.

Аппаратный сбор подготовлен в run-locality-vtune.ps1. VTune в PATH и стандартных каталогах Intel при проверке не обнаружен; сбор не запускался. После установки либо указания существующего vtune.exe:

```powershell
.\run-locality-vtune.ps1 -ImagePath 'C:\Test4K\имя_реального_файла.jpg' -VtunePath 'полный_путь\vtune.exe'
```

Скрипт собирает memory-access последовательно для трёх вариантов и сохраняет журналы, сводки и отчёты по функциям. Для дополнительного анализа доступен -Analysis uarch-exploration. Возможность сбора cache/TLB/stall событий зависит от CPU, версии VTune, драйвера и прав. Скрипт проверяет коды завершения и не выдаёт отсутствие метрики за ноль. Команды отчётов подготовлены по официальному CLI, но на этой машине не проверены, поскольку VTune отсутствует.

Важно: Stopwatch внутри --locality-profile исключает загрузку и три прогрева. VTune собирает весь процесс, включая запуск, загрузку, JIT, прогрев и GC. В аппаратном отчёте нужно анализировать функцию ConvolutionCore и её Line, а не приписывать все события процесса свёртке. Если версия VTune не разрешает .NET-символы, сначала настройте их разрешение; без этого вывод по конкретному циклу преждевременен. 100 повторов в аппаратной нагрузке — увеличение длительности сбора, а не 100 независимых измерений. У всех режимов одинаковое число обработанных пикселей; сравнивайте события на пиксель/вызов, а не только сырые суммы. Проценты stalls нельзя напрямую превращать в процент причины замедления. На гибридном i5-12450H также учитывайте миграцию между P/E-ядрами и частоты.

Интерпретация: Columns медленнее Rows без параллелизма — планировщик вложенных циклов не необходим для возникновения разницы. Рост промахов/задержек памяти в той же вычисляющей функции усиливает объяснение через локальность. Ускорение BlockedColumns одновременно с уменьшением аппаратных задержек — дополнительное подтверждение, но не гарантированный результат. Плитки добавляют накладные расходы циклов; изменение времени само по себе не доказывает только кэш. До реального сбора не писать, что аппаратный профиль подтвердил причину.
